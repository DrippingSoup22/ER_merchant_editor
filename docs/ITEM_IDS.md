`data/item_sort_order.json` (2026-08-01) — `{itemId: {sortId, sortGroupId}}`
for 2771/2784 items, generated by `tools/sort_order_extract` from
`EquipParamWeapon`/`Protector`/`Accessory`/`Goods`/`Gem`'s own `sortId`/
`sortGroupId` columns (every EquipParam table carries these — the game's own
in-menu order) decoded against the fixture save, same house method as
`weapon_reinforce_extract`/`vanilla_shop_lineup_extract` (independent of
EldenRing-SaveForge's own `data.ItemSortKeys`, which needs a CSV dump we
don't have checked out). `app/catalog.ListItems` sorts by
`(subCategoryRank, gameOrderKey(sortGroupId, sortId), id)` — sub-category
block first, then the game's real in-menu order *within* each block
(`itemGroupRank`/`itemGameOrder`). The sub-category dropdown
(`ListSubcategories`) ranks by the same `subCatRank`, so the unfiltered grid
reads exactly as the filter list in order, one contiguous block per
sub-category.

**Changed 2026-08-03** (user-reported): the primary key used to be the raw
`sortGroupId`. Our sub-categories are a *filter overlay* that can span
several `sortGroupId`s, so raw game order interleaved them — key items'
"Quest Items" got split around "Great Runes", leaving only Memory of Grace
under the first heading. Sub-category is now always the outer key (Ashes of
War's `explicitSubCatOrder` affinity buckets are no longer a special case,
just the same rank source). Within a block the game's own order is still
reproduced exactly (weapon menu: Daggers, Throwing Blades, Straight Swords,
… Perfume Bottles). `sortOverrides` (items.go) additionally patches Great
Rune of the Unborn, whose real `sortGroupId` differs from its 6 siblings' —
a FromSoft DLC-data quirk, see the note there. Guarded by
`TestListItemsOrdersByGameSortOrder` +
`TestListItemsGroupsBySubCategoryInFilterOrder`. 13 items have no sort data
(sortId==0/missing rows) and simply sort after everything else via
`noSortRank`.

`data/item_details.json` (2026-08-01) — `{id, description?, location?,
weight?, weapon?, armor?, spell?}` for 2733/2784 items, generated alongside
`items.json` by `tools/itemdb_extract` (`details.go`) straight from
SaveForge's own `db.ItemEntry.Description`/`Weight`/`Weapon`/`Armor`/`Spell`
fields — no new extraction pipeline, just a second projection of the same
data `main()` already has. Powers the item-info popup (right-click a
sellable cell, either grid — see `docs/EDITOR.md`); `app/catalog.ItemDetails(id)`.
Description text: `details.go`'s `effectText` resolves it from SaveForge's
FMG-sourced `db/data.ItemTexts` (keyed by our app id) — this covers ~800
items `db.GetAllItems` returns with an *empty* Description (tools/consumables,
spirit ashes, key items, info notes), which is why coverage jumped from 1920.
Prefers the concise `Description` (short in-game effect) but falls back to the
fuller `Caption` when Description is empty or just the item name — and always
uses `Caption` for spirit ashes (`ashes`), whose Description is only a
summon-type label.
Weapon block additionally carries `guard{Phys,Mag,Fire,Lit,Holy,Boost}`,
`crit`, `scaleArc`, and `passives[]` (`{label,value}` named status effects,
Known-only) — these come from `db/data.WeaponStatsV1ByID` (the richer record
the legacy `db.ItemEntry.Weapon` shape drops), folded in by
`details.go`'s `enrichWeaponV1`. Scaling letter-grades are NOT stored — the
popup derives them from the raw `scaleX` coefficients at render time
(`scalingGrade`, thresholds S≥175/A≥140/B≥90/C≥60/D≥25). Consumables carry
no *structured* scaling/FP data (SaveForge computes weapon stats only); the
popup renders those items as a single description box, no scaling/FP
placeholders. Ammunition (`arrows_and_bolts`) shares the weapon table but the
popup shows an attack-only panel (no guard/scaling/requires).
Spell block (`{fpCost,slots,reqInt,reqFai,reqArc}`) is now sourced from
`data/spell_stats.json` (MagicParam ground truth via
`tools/spell_stats_extract`), overriding SaveForge's hand-curated spell table
in `details.go` — it matches for every curated spell (0 mismatches) and adds
the ~42 Shadow-of-the-Erdtree DLC spells the curated table omitted, so all 213
sorceries/incantations now show cost/requirements. `spell_stats.json` is a
dev-side generation input (read by `itemdb_extract`, not embedded at runtime).
Damage throwables (Fire Pot, Lightning Pot, throwing daggers/stones — the
`tools` category, 74 items) carry a `scaling` block (`{str,dex,int,fai,arc}`
raw coefficients) from `data/consumable_scaling.json`
(`tools/consumable_scaling_extract`): each throwable's damage is backed by a
hidden virtual weapon (`EquipParamGoods.refVirtualWepId` -> an
`EquipParamWeapon` row), whose `correctX` values are the scaling. The popup
grades them with the same `scalingGrade` breakpoints as weapons — note the
wiki's per-item damage-curve grades can differ by a letter for some throwables
(e.g. Fire Pot shows Str B here vs Str A on Fextralife); graded from raw
coefficients for consistency with weapon cards by explicit user decision
(2026-08-03). Also a dev-side generation input, not embedded.

`data/weapon_reinforce_rates.json` (2026-08-03) — `{columns, types:
{reinforceTypeId: [[15 rates] per level]}, weapons: {itemId: reinforceTypeId}}`
from `tools/weapon_reinforce_rates_extract` (16 curves, 479 weapons). Embedded.
item_details' weapon stats are the base (+0); this stores the per-level
multiplier curve the game applies (`ReinforceParamWeapon` attack/scaling/
guard-cut rate columns), so the item-info popup shows a weapon at its actual
"+N" (`catalog.ReinforcedWeapon(id, level, base)`; catalog grid uses the
clamped PickLevel, a merchant row its own level). Each weapon uses its OWN
`reinforceTypeId` curve — the correct "standard scaling" for a base merchant
weapon (no Ash-of-War affinity infusion changes the base row); standard
weapons are type 0 (+25, scaling ×1.5 / attack ×2.45 at max), somber type 2200
(+10). Guard boost / crit have no rate column and stay at base.
`TestReinforcedWeaponScalesByLevel` guards the math (CI-runnable, no fixture).

## Ban-risk tier classification, `key_items` (2026-07-31, user concern: "clueless user" bricking their online status)

Deep-dived `key_items` (349 entries) specifically since a merchant row can
be swapped to sell any catalog item, including these. Cross-checked two
sources: (1) general ban-report research (r/Eldenring, PSA threads), (2)
`EldenRing-SaveForge`'s own dedicated ban-risk subsystem
(`spec/32-ban-risk-system.md` + `backend/db/data/key_items.go`), which
curates real per-item ban history far more precisely than generic search.

**Scoping correction, important**: FromSoftware's actual Elden Ring
anti-cheat is a **server-side save-state check** (not Steam's Easy
Anti-Cheat, which is PC-only, irrelevant to this PS4/PS5-only project). It
bans for (a) items that cannot exist through any legitimate path (cut/
unreleased content) and (b) impossible *values* (runes >999,999,999,
stats >99, upgrade levels beyond max, quantities beyond
`MaxInventory`). Since this tool only edits *what a merchant sells* — the
player still buys through the real game engine, which enforces its own
caps exactly as for a legitimate purchase — the "impossible value" ban
class does **not** apply to this tool's attack surface. Only "impossible
identity" does. Also checked and ruled out: DLC-owned key items are safe
to sell even to accounts without Shadow of the Erdtree — confirmed via

## Critical gotcha: two ID encodings (+ a third for shop rows)

- *Item-ID space* (what `items.json` is keyed on): `0x00`=weapon,
  `0x10`=armor, `0x20`=talisman, `0x40`=goods, `0x80`=Ash of War (high nibble).
- *GaItem handle space* (stackable goods/talismans in inventory/storage
  records elsewhere in the save): `0x80`=weapon, `0x90`=armor,
  `0xA0`=talisman, `0xB0`=goods, `0xC0`=AoW.
- **`ShopLineupParam`'s `equipId`** is neither — it's a raw row ID into the
  per-category `EquipParam*` table named by the row's `equipType` field.
  Convert: `item_id = equipId + offset[equipType]`, `{0: 0x00000000 weapon,
  1: 0x10000000 armor, 2: 0x20000000 talisman, 3: 0x40000000 goods,
  4: 0x80000000 Ash of War}` — confirmed empirically for all 5 known types,
  applied automatically by `tools/savescan.py rows`. `equipType` 5/6 exist
  in real data (weapon-locked unique skills) but aren't in Paramdex's enum
  — offset unknown, left unmapped (negligible: 1 row total).
- Inverse (`equip_ref_for_item_id`, the `find-item` CLI subcommand) is
  exact — round-trip-verified against all 2772 items + all 1247 resolvable
  shop rows, 0 mismatches. 7/2772 items (0.25%) share a name across
  categories (e.g. a sorcery and an AoW both called "Glintstone Pebble") —
  `find-item` returns every match, caller must disambiguate.

## Weapon reinforcement levels (2026-07-28)

**Confirmed empirically, not assumed.** `items.json`'s weapon-table entries
(`melee_armaments`/`shields`/`ranged_and_catalysts`, 479 items — equipType
0) are always the "+0, Standard affinity" variant: every sampled base id is
an exact multiple of 10000 (e.g. Zweihander `1010000`... value stored is
`4040000`, still a clean multiple). A reinforced ("+N") item's id is
`base_id + N` — confirmed via `EquipParamWeapon`'s `reinforceTypeId` field
cross-referenced against which `ReinforceParamWeapon` rows actually exist
(`row_id = reinforceTypeId + level`, contiguous from 0 — e.g. Zweihander
`reinforceTypeId=0` has rows `0..25`, Moonveil `reinforceTypeId=2200` has
rows `2200..2210`). No "+10 vs +25 by subcategory" guessing: 286/479 max
+25 (standard/Smithing Stones), 192/479 max +10 (somber/Somber Smithing
Stones — bows, staves, seals, torches, and most legendary/boss-drop melee
weapons), 1/479 max +0 (Meteorite Staff — genuinely non-reinforceable).
Both tables are embedded in every save's regulation.bin (confirmed via
`tools/savescan.py list save_files/vanilla_fresh_character.dat`), decoded
the same generic way as every other table here.

`data/weapon_reinforce.json` (`{itemId, maxLevel}`) is generated once by
`tools/weapon_reinforce_extract` from this and treated as static game data
(like `items.json` itself), not re-derived per loaded save.

**Real bug found and fixed while building this**: `tools/paramdex_schema.py`
(the shared PARAMDEF schema builder, used by every `tools/*_extract` tool)
mis-decoded `EquipParamWeapon` by 2 bytes — its bitfield-grouping only
merged *same-typed* consecutive bitfields into one storage byte, but
`EquipParamWeapon`'s very first fields are `u8 disableParam_NT:1` +
`dummy8 disableParamReserve1:7` (different declared types, same real byte
— `dummy8` is the generic "reserved bits" marker regardless of the group's
real anchor type, a pattern the 3 previously-decoded tables never hit).
Caught by comparing the schema's computed `row_size` (666) against the
*real* row spacing measured from consecutive `EquipParamWeapon` row
`data_offset`s in our own fixture (664) — every garbage-looking decoded
value (a denormal `weight`, a huge `weaponWeightRate`) traced back to this.
Fixed by treating `dummy8` as compatible with any bitfield group.

**In-game tested 2026-08-02** (real user save-load, not offline-only):
leveling itself is correct. Found a real, separate bug on reload: `items.json`
only indexes +0 base ids, so `app/catalog`'s row decode couldn't resolve a
`base_id + N` equipId at all -- a leveled row showed a blank icon and its
stale pre-edit label in the merchant grid (the save/game itself were fine;
this was our own re-read only). Fixed in `app/catalog/items.go`
(`resolveItemIDWithLevel`, falls back to `rawID - rawID%10000` validated
against the item's real `MaxUpgradeLevel`) -- see `CLAUDE.md`'s editor
section for the full fix writeup.
